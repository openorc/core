# RQ Worker Agent Context

## Boundary

Workers own queue entrypoints, queue payload decoding, invocation of shared application services, and queue/transport integration.

They do not own business logic, workflow authority, the Task state machine, provider/runtime calls that bypass adapters/services, or durable copies of workflow truth.

## Shared operation invocation boundary (issue #86)

Logical operations cross process surfaces only through the strictly typed invocation boundary in `openorc.workers.invocation`: a closed operation-kind discriminator, kind-specific typed payloads, strict decoding before any effect, and one shared dispatcher (`invoke_operation`) with an explicit kind-to-handler table. The transport-facing submission seam distinguishes accepted-for-delivery, known refusal (typed reason), and uncertain submission; acceptance is never completion, external effect, or retry authorization, and queue/job IDs are never operation authority.

- Both execution modes use the same kind/handler mapping: regular mode through the bounded API-local executor owned by the serving process, queue mode through the canonical default queue and this worker process.
- The queue-mode detached-turn observation seam (issue #346): this process never hosts an observer. Resolving the registration seam in queue mode yields the remote registrar proxy (`openorc.workers.queue_observer_registration`) over the private authenticated deployment-only handshake against the serving API/control-plane process that hosts the ONE long-lived observation host; a queue dispatch worker must positively attest a live exact-session observation registration BEFORE any detached admission (the native Hub enqueue is adapter-owned), never treats a sent request as registration success, and must not enqueue when it cannot attest a live observer registration. Every non-acknowledged outcome raises the same typed refusal taxonomy as a local host. Since #347's transport parity the F1 RQ handlers run the same detached dispatch as regular mode — the queue-mode worker exits after the durable admission and never hosts a model turn or an in-process result routing — and the hosting API process additionally performs the bounded durable restart reconciliation (READY bindings through their immutable identity, CONNECTING initialization receipts through their provisional identity, unprovable candidates skipped without recreation or redispatch).
- The RQ worker process must be explicitly in queue execution mode and refuses regular-mode startup; mode selection alone never makes in-flight work safe to replay.
- The envelope and executor make no Task-state, currentness, or authorization decisions; that judgment belongs to the application services handlers invoke with process-local dependencies.
- The Task-workflow handlers delegate to the transport-neutral application coordinator (`openorc.services.task_workflow_operation_coordinator`), which invokes Level 1 through the single composition seam, preserves ordinary success, and on an applicable operational failure reports the invocation's own Level 1-produced attempt identity and currentness to the Level 2 triage service. Handlers never choose recovery, retry, or blocking, and Level 2's dispositions are authoritative over this surface; the coordinator re-raises the original exception so this process's sanitized, unchained worker-error report stays intact.
- The Task-less GitHub handlers (F9, issue #255) invoke the existing webhook-dispatch and reconciliation/recovery application services directly with process-local dependencies and only the decoded delivery GUID or scheduling tick. They are not enrolled in Level 2/3 operational-failure triage: their failures stay contained by this boundary's sanitized execution-error reporting, and the services' own durable outstanding-work semantics own recovery.
- The post-terminal cleanup handler (F10, issues #256/#317/#344/#345, `openorc.workers.task_cleanup_operations`) invokes the shared authoritative terminal finalization service with only the decoded scoped Workspace/Task identifiers plus the EXPLICIT cleanup dispatch selection resolved by the executing process (both execution modes resolve the detached registrar seam — the process-local observation host in regular mode, the #346 remote registrar proxy in queue mode; a registrar that cannot resolve is the observation-unavailable selection — positively skipping the optional cleanup with no claim, no receipt, and no blocking send, never an inferred blocking fallback; the detached selection additionally carries the process's ONE post-commit completion handoff, which the dispatching invocation routes when its acknowledgement attach consumes a staged early completion, and which the same handoff's `TERMINAL_CLEANUP` route re-invokes after an independently observed settlement) and re-derives every authority, identity, and safety fact from durable state at execution time. Like the GitHub family it is not enrolled in Level 2/3 triage: the finalizer's idempotent authority rechecks, the one-shot cleanup claim (a concurrently unsettled claim inside its finite deadline defers the archival to its owning attempt; a settled or past-deadline claim never re-dispatches), and this boundary's sanitized execution-error reporting own every outcome, and the terminal seams arrange its submission through the F1-backed bridge (`F1TerminalFinalizationSubmission`) strictly post-commit for a newly committed terminalization only — a refused delivery falls back in-process to the same archive-only finalization, an uncertain submission is never replayed here, and a silently dead worker leaves the commitment unfinished until a later explicitly invoked finalizer (the accepted system-wide v1 limitation recorded on issue #317).
- The F11 Task-queue wake handler (issue #257, `openorc.workers.task_queue_operations`) invokes the ONE bounded FIFO admission processor (`task_start.reevaluate_queued_tasks`) with process-local dependencies and, strictly after its committed admissions, submits one typed planning-bootstrap continuation per admitted candidate from that outcome's exact post-claim facts, plus one bounded continuation wake when the sweep hit its candidate budget before exhausting the queued set (the payload's continuation cursor is a paging hint, never authority). Like the GitHub and cleanup families it is not enrolled in Level 2/3 triage: sweep failures stay contained by this boundary's sanitized execution-error reporting and the durable queued facts own recovery. The F1-backed `F1TaskQueueWakeSubmission` bridge implements the shared `task_queue_wake` seam for every capacity-relevant service arrangement, and the queue-mode hosting process runs `arrange_task_queue_recovery` beside its startup reconciliation: lost wakes are re-arranged from the persisted queued facts, and a lost planning-bootstrap handoff is submitted only where the E1b one-shot claim positively proves the bootstrap was never consumed — a claimed, admitted, or uncertain runtime turn is never replayed by recovery.
- The ONE post-commit completion handoff (issues #324/#333/#334/#335) is built by the worker-layer builder `build_detached_completion_handoff` — services never build invocation payloads — and injected into the observation host, the E6 detached dispatch, the bootstrap preparation, and the detached plan-production dispatches. It routes each settled validated completion by its explicit operation family: the #324 readiness-resumed bootstrap submission, the E6 initial-IMPLEMENT exact-head `PR_AUTHORIZATION` presentation invoked through the existing F5f service under the F5b coordinator with the fresh committed-state token seed and the durable Workspace Owner identity, the #334 workspace-PREPARE transition continuation — the settled `prepared` stage is the only authority, the same-session planning-context reconstruction runs from committed state under the F5b coordinator with the transition-phase attempt identity (a positively detected reconstruction failure reports under the bootstrap claim's transition family and escalates exactly as the blocking path does, never an unreported failure stranded on a prepared stage), the next typed `TASK_PLANNING_BOOTSTRAP_AND_INITIAL_PLAN` invocation is submitted with the fresh post-tail token — and the #335 plan-result routes, which submit the existing typed `TASK_PLANNING_REVIEW` round from committed state after a settled initial-PLAN or REVISE result, and the #337 PR_COMPOSE route, which performs the settled composition's bounded publication through the existing owning service (the one route consuming the settlement's in-memory validated `pr_result` — the v1 persistence decision stores no title/body) and then submits the existing typed `TASK_PR_REVIEW` from committed state; the #338 review-result route resolves the settled review decision's continuation by the reserved attempt's durable subject flavor (the planning continuation for a plan-subject iteration and the detached E9 remediation enqueue on the exact Task checkout for an in-budget PR/head change request), and the #338 PR-remediation route re-proves the settled round and verifies the branch claim and the SAME canonical PR's GitHub-confirmed new head through the existing B7 reconciliation — a positively unverifiable round installs the atomic Level 3 BLOCK_RESOLUTION block through the shared exceptional-blocking foundation (never a Level 2 identity for a succeeded Execution) a failed or uncertain reconciliation read installing the same atomic Level 3 BLOCK_RESOLUTION block under the escalation reason vocabulary, and a GitHub-confirmed terminal pull-request state routing through the existing authoritative terminal-reconciliation ownership (the trusted #229 cancellation entrypoint for a confirmed closed-unmerged record; zero durable mutation for a confirmed merge) — and only then a still-OPEN record with a GitHub-confirmed new head submits the next typed `TASK_PR_REVIEW` through F1 for that confirmed head. Every input is re-derived from committed state — the single deliberate #337 exception is the PR_COMPOSE family's in-memory `validated_result` parameter — a failed/uncertain routing or submission is transport information only, never Task truth, and never permits a blind re-enqueue; a settled family without a wired route is a fail-closed conflict.
- The E6 composition (`TASK_AUTHORIZED_IMPLEMENTATION`) dispatches the implementation as one detached agent turn and returns after the durable admission in both execution modes (issue #347); the independently observed completion settles the attempt and the completion handoff owns the presentation. The bootstrap composition (`TASK_PLANNING_BOOTSTRAP_AND_INITIAL_PLAN`) likewise suspends at the detached establishment (#324), at the detached workspace PREPARE (#334), and at the detached initial-PLAN dispatch (#335, which returns after the admission instead of producing inline and submitting the review round); the re-submitted continuation classifies a `ready_for_planning` stage with no published plan revision as the resolved bootstrap whose prepared outcome is re-derived from durable state with zero bootstrap runtime effects. The planning-review composition (`TASK_PLANNING_REVIEW`) dispatches the REVIEW as one detached turn (issue #336) and returns after the durable admission — no blocking send and no in-process decision; the independently observed completion settles the decision through the owning E3b settlement and the handoff owns the continuations (the accepted-plan IMPLEMENTATION_AUTHORIZATION presentation, the detached Producer REVISE dispatch on an in-budget change request, and nothing on exhaustion) from committed state. The PR-composition composition (`TASK_PR_COMPOSITION`) likewise dispatches the approved-head PR_COMPOSE as one detached turn (issue #337) and returns after the durable admission — no blocking realization and no model-turn wait; the independently observed completion settles the validated `pr_result` and the handoff owns the bounded publication and the typed PR-review submission from committed state, while the narrow interrupted-publication continuation (an existing canonical record at admission) reconciles and finalizes inline and the composition submits the PR review for it. The regular-mode PR-review composition (`TASK_PR_REVIEW`) likewise dispatches the canonical REVIEW as one detached turn (issue #338) and returns after the durable admission — no blocking send, no in-process decision, and no `while True` remediation re-entry; the independently observed completion settles the validated `review_result` through the owning PR-review settlement and the handoff owns the detached E9 remediation enqueue on an in-budget change request (whose own observed completion re-proves the settled round, verifies the GitHub-confirmed new head, and submits the next typed PR review from committed state), with the MERGE_DECISION and REVIEW_RESOLUTION gates owning their Owner seams. The queue-mode interim keeps the blocking dispatch/decision/remediation loop and the blocking compose-publish-review until #328.

- The common detached-operation rule (issues #325/#340) every detached family obeys: the original durable operation claim remains authority; the Hub receipt tracks only the admitted run; the validated completion routes to the original owning service and its durable atomic settlement; only committed state authorizes F1 continuation; Level 1/2/3 and the v1 missing-event/no-blind-replay limits are preserved. The Task-workflow compositions route every ordinary model turn — including the F5c authorized-implementation retry, whose registered F1 operation is directly invocable for an already-due F4 authorization — through the owning services' detached dispatches and return after the durable admission in both execution modes (issue #347); the queue-mode worker exits after the admission and the API-hosted observer settles the completion, and F12 (#316) owns submitting due authorized retries in either mode.

## Process lifecycle and fork boundary (issues #346/#347)

- The worker builds its `OperationDependencies` inside each executing job (`execute_operation_job`), after any RQ fork: the database pool is the PID-scoped lazy process-local boundary and no pool, client, or live handle is ever carried across a fork. The resolved observation registrar in queue mode is the stateless #346 remote proxy (transport plus deployment secret only).
- Startup: the worker requires queue execution mode, connects to the configured Valkey backend, and runs the canonical queues. It never hosts an observer; the serving API/control-plane process hosts the ONE long-lived detached-turn observation host, exposes the private authenticated registration handshake, and performs the bounded durable restart reconciliation at startup.
- Shutdown/restart: RQ status is transport evidence only. A job that dies before attaching its admission leaves the accepted v1 unresolved state (no silent-worker-death recovery); an admitted or uncertain detached turn stays claimed for the independently observed settlement. Restart reconciliation re-proves durable outstanding receipts through the registration gates — it never recreates sessions, never redispatches, and never invents identity. No automatic RQ retries are configured anywhere: an uncertain admission is never replayed by the queue.

## Replay and durability rules

Assume every workflow-changing job can be delayed or replayed. The invoked service must revalidate current Task state, exact subject/gate/request, external side-effect completion, session binding, and authorization before acting.

A replayed job must never create replacement Task sessions, resend a known-delivered runtime message, create a second canonical PR, apply stale acceptance/gate decisions, or duplicate GitHub mutations.

RQ status is not workflow truth. Postgres is. Workers must be restartable without reconstructing domain state from process memory.

## Queue telemetry

- The worker process initializes observability once per process at start and performs the terminal shutdown/flush in `run_worker`'s `finally`; telemetry misconfiguration fails fast like other configuration errors, and runtime export failures never crash the worker.
- Job entrypoints create spans through `observability.tracing.application_tracer` with the RQ job identity from the safe attribute vocabulary (`openorc.rq_job_id`). Queue handoff may propagate trace context through job metadata where it can do so safely; queue state is never workflow truth and trace context is telemetry-only.

Read services plus the relevant adapter and persistence guides for queue behavior changes.

## Queue naming and backend contract

- `openorc:` is the stable application-level RQ queue prefix. Deployment isolation is provided by the Redis/Valkey namespace selected by `VALKEY_URL`. In the current reference/local setup this may be a Redis DB index; another deployment may use a dedicated instance/service.
- Canonical queue names are defined in `src/openorc/workers/queues.py`; the canonical default queue is `openorc:default`.
- The queue backend contract is Redis-compatibility through `VALKEY_URL`; no server binary or server version is pinned. The pinned `rq`/`redis` packages are application dependencies under the repository dependency policy, not server-version indicators.
