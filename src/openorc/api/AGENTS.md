# FastAPI Transport Agent Context

## Boundary

This subtree owns HTTP routing, auth/session dependency extraction, request parsing/validation, response serialization, HTTP error mapping, wire DTOs, and authorized SSE endpoints.

It does not own workflow transitions, review/session lifecycle decisions, GitHub reconciliation policy, retry/idempotency policy, persistence rules, or direct external orchestration that bypasses services.

## Rules

- Routers call shared application services.
- Do not duplicate business/domain validation that must also apply to workers or future transports.
- Resolve authentication and Workspace scope before invoking application operations.
- Browser clients never call Agent Runtimes directly through hidden API shortcuts.
- Runtime/provider URLs exposed to the UI are navigation affordances only.
- SSE is live delivery, not durable workflow truth.
- FastAPI `BackgroundTasks` is not used for deferred or workflow execution; that work is submitted through the shared operation-invocation boundary (`openorc.workers.invocation`), delivered by the bounded API-local executor in regular execution mode (default) or by RQ/Valkey queues in queue mode, and always resolved by shared application services.
- In regular execution mode the lifespan owns exactly one bounded local executor per serving process; no executor is created at import, factory construction, or request time, and API async/event-loop handlers only submit — blocking service/DB/runtime work never runs inline (issue #86). The same lifespan owns the process's hub-run observation host beside the executor (started before it, disposed after it drained) (issue #323). In queue execution mode the serving process still creates no executor, but it hosts the ONE long-lived detached-turn observation host itself — never inside an RQ workhorse — runs its one bounded durable restart reconciliation at start, and serves the private authenticated deployment-only registration handshake (`/internal/observer/registrations`) a queue dispatch worker must positively attest before any detached admission (issue #346). The handshake is private/authenticated and nonpublic, is never an application command or Owner authority, and fails closed on an unavailable host; the v1 deployment assumption is one API instance per deployment (multiple instances must not silently split in-memory session registrations).
- v1 persistence is synchronous: async/event-loop handlers must not perform blocking database I/O directly. In both execution modes the lifespan additionally runs two bounded recovery passes off the event loop at startup: the F11 Task-queue recovery (issue #257) — lost capacity wakes are re-arranged from the persisted queued facts, and a lost planning-bootstrap handoff is recovered only where the durable one-shot claim positively proves the bootstrap was never consumed — and the F12 authorized-retry recovery (issue #316), which resubmits the same typed F1 retry invocation for each still-outstanding durably authorized Level 2 retry without touching the F11 FIFO or its capacity processor and never clearing or rewriting the retry ledger. A failed pass is contained and the next supported trigger revisits the rest. Regular mode delivers the recovered arrangements through its own bounded local executor; queue mode submits them beside the durable restart reconciliation.
- Provider webhook ingress routes (e.g. `POST /api/github/webhooks`, issue #61) are authenticated by the provider's own signature material, not by Supabase Auth: the route bounds the body while reading it (an oversized request is rejected without ever being fully buffered; a Content-Length precheck is only an additional fast rejection), reads the exact raw request bytes and the required provider headers, delegates the blocking intake — process-local pool acquisition included — off the event loop (threadpool), and maps only typed intake outcomes/errors to HTTP. Signature failures map to a uniform, detail-free rejection; the route contains no reconciliation, queue, or workflow logic.
- The Task discussion and conversation routes (issue #339) are the first task-scoped transport surface: the discussion POST runs the service's synchronous authorization preflight (typed HTTP errors for every immediately detectable failure) and then admits asynchronously through the shared operation-submitting boundary — a 202 acknowledges authorization and transport acceptance only, never delivery, and never a model reply; a positively refused submission releases the prepared receipt through the service and maps to the failure class, and an uncertain submission fails without ever claiming non-delivery. The correlated receipt-status projection reports the actual admission/refusal lifecycle, and the conversation read is one transient authorized adapter read that records nothing durable.
- The Owner Task-command routes (issue #378) are the public command surface for issue-level intake and queue-first Start: both commands are synchronous sync-handler delegations to the existing authoritative services (`task_intake`, `task_start`) with the GitHub App boundary composed per request by the `api/dependencies/github_app_client.py` fail-closed composition. The command responses project the services' authoritative post-write snapshots only — never a re-derived current-state projection (the Task-read resource owns subsequent retrieval, and immediate FIFO admission before the response must never re-derive the body) and never a command-status ledger. The Start response documents the committed `queued` entry and the separately-typed post-commit queue-wake delivery evidence the owning service captured from the F1 seam; no event is ever emitted from HTTP (the `task_started` audit fact stays inside the Start service).
- The ordinary OwnerGate decision routes (issue #379) are the public command surface for the G2b ordinary gate `approve` action: three synchronous sync-handler delegations to the existing dedicated services (`task_implementation_authorization`, `task_pr_authorization`, `task_merge_lifecycle`) with the GitHub App and Profile user-token boundaries composed per request fail-closed, the already-owned E5→E6/E7→E8 continuation helpers and the merge's F10/F12 submission seams composed over the process `OperationSubmitter`, and the merge service's classified outcome kinds mapped verbatim (a confirmed merge may truthfully coexist with a committed-but-unarchived terminalization; `merge_commit_sha` stays absent when reconciliation confirmed without it). Responses project the services' authoritative post-write snapshots plus separately-typed delivery evidence only — a refused or uncertain continuation never fails the committed approval; no action-menu re-derivation (the Task-read resource owns the G2b projection), no cancellation routes (G3c issue #380 exclusively owns the shared `cancel_task` command), and no event is ever emitted from HTTP.
- The Task-level Owner Abort and shared Cancel Task routes (issue #380) are the public command surface for the G2b Task-level `abort` action and the shared `cancel_task` offering: two synchronous sync-handler delegations with state_token-only bodies — Abort delegates to `task_abort.abort_task_activity_for_owner`, whose establish transaction derives the exact interruption targets from durable admitted-operation evidence (never a client-selected role list, never settlement evidence) and dispatches per-target Interrupts strictly post-commit through the composition-rooted `cline_attachment.OwnerAbortInterruptDispatcher` seam (expected attachment-stage failures are handled within that per-target boundary — durable non-delivery `failed` for a definitive failure, `unknown` preserving uncertainty for an uncertain attachment outcome, never settlement, remaining targets still dispatched), while the ONE shared Cancel command (`task_cancellation.cancel_task`, no gate identifier, no gate-scoped cancel route — G3d #381 reuses it) serves both Task-level and current-gate offerings with the GitHub App and Profile user-token boundaries and the F10 terminal-finalization seam composed per request. Responses project the services' authoritative post-write snapshots plus separately-typed per-target dispatch/close-obligation facts only — committed terminalization never implies archived/capacity-released status, an acknowledged Interrupt is never settlement, and no event is ever emitted from HTTP.
- The exceptional OwnerGate action routes (G3d, issue #381) are the public command surface for the fixed Level 3 gate menus' remaining executable actions, one synchronous sync-handler delegation per G2b gate-scoped action token with the shared `OwnerGateActionCommand` state_token-only body: `ignore` (pending `GITHUB_ISSUE_CHANGE`) delegates to `task_source_change_ignore.ignore_github_source_change` with the GitHub App boundary composed per request and maps the committed Ignore verbatim including the interrupted boundary's re-presented approval gate subject facts (no continuation submission exists — the presented gate is the committed handoff), `continue` (pending `COST_LIMIT`) delegates to `task_owner_cost_continue.continue_task_after_cost_limit`, and `resume` (pending `OWNER_ABORT`) delegates to `task_owner_resume.resume_task_after_abort` — both then arranging the ONE shared post-commit one-shot session-resume continuation through `submit_task_session_resume_after_authorization` over the process `OperationSubmitter`, documenting `continuation_outcome` as separately-typed delivery evidence that never fails or reverses the committed authorization. Later continuation outcomes and operation settlement are new Level 1/2/3 episodes observed through the G2b reads — HTTP success never implies a model result, settled gates/blocks are never reopened, every exceptional-gate `cancel_task` offering reuses the single shared Cancel command, status/diagnostics stay on the existing G2b Task/pending-interaction reads (no gate-scoped cancellation or diagnostics routes), and no event is ever emitted from HTTP.
- Provider webhook ingress deployment expectations — HTTPS delivery URL, provider SSL verification enabled, a high-entropy webhook secret, GitHub's 10-second delivery deadline, and durable-accept-before-acknowledge — are deployment assumptions of this boundary documented in the repository README (issue #122); they are deployment/provider-facing facts, not application workflow logic.
- API contracts consumed by the SPA require coordinated changes with `apps/app/AGENTS.md`.
