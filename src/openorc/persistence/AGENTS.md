# Persistence Agent Context

## Boundary

Persistence owns durable representation and repository/data-access mechanics for OpenOrc control-plane state. It does not define product workflow semantics merely because a table or constraint exists.

## Rules

- Postgres is the durable source for OpenOrc workflow/control state.
- Preserve Workspace scope explicitly on Workspace-owned operational data where practical.
- Enforce durable uniqueness/identity constraints that protect domain invariants, including at most one current/non-archived Task per repository issue.
- Store stable external identifiers and exact SHAs needed for reconciliation; mutable display fields must not be sole identity.
- Do not store runtime conversational context or chain-of-thought as workflow state.
- Raw secrets do not belong in ordinary application tables.
- Schema changes must remain aligned with `supabase/migrations/` and tests.
- Database shape must not become an excuse to bypass domain/service rules.

## v1 driver and connection conventions

These are durable Phase 1 conventions. Later issues inherit them; do not re-litigate them issue-by-issue. Changing one is a deliberate architecture decision, not an implementation detail.

- Postgres is accessed through synchronous psycopg 3 with `psycopg_pool.ConnectionPool`. No async psycopg API and no parallel sync/async persistence implementations exist at this boundary. The synchronous foundation serves API/service code and RQ workers alike.
- Pool ownership is strictly process-local. A pool belongs to exactly one OS process, and the `ConnectionPool` object must be created in the OS process that uses it, after any fork that process has gone through. Never construct a pool anywhere it could be inherited across an RQ fork boundary (the default RQ worker forks a child process per job): an RQ parent must not establish database pool/connection state before forking its work horse. Process surfaces own the lifespan/ownership wiring that satisfies this invariant within their process.
- Pool access is process-aware: the accessor tracks the owning PID and fails closed on PID change. A changed process identity can never reuse, replace, or close the previous pool; a stale fork-inherited pool is abandoned untouched. A process creates a pool through the explicit fresh-pool path only when its parent established no pool before the fork.
- Pool size bounds are per process, not deployment-wide. Deployment sizing must account for process count × pool size.
- Connections are pooler-neutral by default: `prepare_threshold=None`, no dependence on `search_path`, and no session-local state (no session `SET`/GUCs). Pooler mode (direct/session/transaction) is a deployment concern and must never leak into persistence code or domain meaning.
- Transactions are thin and composable: yield one connection and delegate commit-on-success, rollback-on-error, and connection-return to psycopg/psycopg_pool connection-context semantics. OpenOrc does not duplicate transaction machinery, and repositories do not establish auto-commit behavior.
- No external call (GitHub, Cline, model inference, or any other external system) may occur while a database transaction is open.
- Row locking is narrow and deliberate: repositories author semantic `SELECT ... FOR UPDATE` operations inside short transactions where the domain requires them. There is no generic lock-row or query-builder locking abstraction.
- `READ COMMITTED` is the normal isolation level; the persistence foundation does not customize isolation.

## SQL and data conventions

- Repositories are explicit SQL repositories. Table references use fully qualified `openorc.*` names, values are always parameterized, and `psycopg.sql` composition is used only where dynamic identifiers are genuinely required. No f-string SQL.
- OpenOrc-owned application tables live in the dedicated `openorc` schema. Migration authority, grant posture, and the append-only migration rule are owned by `supabase/AGENTS.md`; persistence code never mutates committed migration history.
- Internal domain records use UUID primary keys unless an explicit 1:1 infrastructure identity deliberately reuses another system's UUID (e.g. `Profile` mapping to the Supabase Auth user UUID).
- Workflow/type vocabularies are Python enums/value objects enforced in the database as text columns plus CHECK constraints, never native Postgres ENUMs.
- Instants are stored as `TIMESTAMPTZ`. Python datetimes crossing the persistence boundary are timezone-aware and normalized to UTC; naive datetimes are rejected. `utc_now()`-style helpers are low-level utilities, not workflow-clock semantics.

## Ownership and repository identity conventions (Phase 1)

- The ownership tables (`profiles`, `workspaces`, `projects`, `repositories`) live in the `openorc` schema and map to `openorc.domain.ownership` objects. Instants read from Postgres are normalized to UTC at the mapping boundary.
- `profiles.id` is the caller-supplied Supabase Auth user UUID (1:1 by value). OpenOrc migrations never create foreign keys into Supabase-managed schemas (`auth`, `storage`, ...); domain references point at `openorc.profiles`.
- Workspace-owned child rows carry a direct `workspace_id`. Where the parent also carries `workspace_id`, a composite foreign key `(parent_id, workspace_id) → parent (id, workspace_id)` enforces that the direct scope agrees with parent ownership. This is the durable pattern for later Workspace-owned tables.
- External identities that must be canonical per Workspace use `UNIQUE (workspace_id, <stable external identity>)` (for example the GitHub repository ID). Mutable observed metadata changes through explicit repository UPDATE statements that also advance `updated_at`; identity columns are never part of such updates.
- Violated durable invariants surface as driver exceptions (`UniqueViolation`, `ForeignKeyViolation`, ...). Translating them into typed application errors is a service-layer concern, not a persistence one.

## Connection and workflow role binding conventions (Phase 1)

These conventions are established by the Connection/role-binding persistence (issue #20); later issues inherit them.

- `connections` and `workflow_role_bindings` map to `openorc.domain.connections` objects. Both carry a direct `workspace_id`; the composite foreign key `(connection_id, workspace_id) → connections (id, workspace_id)` keeps a binding's direct scope in agreement with the bound Connection's Workspace.
- Raw OpenOrc-owned secrets do not live in ordinary application tables. OpenOrc-owned authentication is represented only through the nullable opaque `connections.auth_reference` boundary: NULL means no OpenOrc-owned auth reference is currently configured, non-NULL means one was supplied. Validation, expiry, revocation, and authentication lifecycle state are later functionality that can actually determine those facts — do not persist speculative auth status vocabulary. Runtime-owned provider/MCP/tool credentials remain runtime-owned and are never modeled as OpenOrc credential records.
- `connections.safe_config` is the non-secret Owner configuration container (jsonb, defaults empty) with canonical JSON-object semantics: string keys at every level, JSON-representable values only, sequences normalized to lists — nothing relies on silent key coercion. Persistence applies no credential key filtering; the contract is simply that secret material does not belong there, and concrete adapter configuration schemas enforce allowed fields when they exist. Every jsonb write goes through `psycopg.types.json.Jsonb` at the persistence boundary: psycopg 3 does not adapt plain mappings to jsonb without an explicit wrapper.
- `connections.enabled` is the Owner-controlled eligibility switch (default true): OpenOrc is permitted to use the Connection. It never encodes runtime reachability, health, initialization, READY, or WORKING state — no runtime status vocabulary is persisted.
- `connections.session_capacity` is Owner-configured OpenOrc admission control scoped to the Connection (default 1: concurrency is explicitly enabled by the Owner, never assumed). It is never discovered from the runtime. Capacity admission later compares this against occupied TaskAgentSessions; do not add speculative capacity indexes.
- `reported_provider`/`reported_model` are nullable opaque runtime-reported observation strings — never configuration authority, never enums. A future OpenOrc-side selection capability would add separate `configured_*` concepts rather than repurposing these fields.
- A workflow role binding is mutable per-role configuration: `unique (workspace_id, role)` gives exactly one binding per workflow role in v1 (no runtime pools, no failover). Producer and Reviewer bindings are independent rows that may reference the same Connection or separate Connections. The binding carries only workspace/role/connection identity and timestamps; per-role session configuration is added only when a real configurable property exists. Repository upserts (`set_role_binding`) preserve binding identity and `created_at` — a configuration change, not historical replacement.

## Task aggregate conventions (Phase 1)

These conventions are established by the Task persistence (issue #21); later issues inherit them.

- `openorc.tasks` maps to `openorc.domain.tasks.Task` and carries a direct `workspace_id`; the composite foreign key `(repository_id, workspace_id) → repositories (id, workspace_id)` keeps the Task's direct scope in agreement with the Repository's Workspace. The repositories hook (`unique (id, workspace_id)`) was added by the Task migration; other Repository children depend on it.
- Task identity and current-attempt uniqueness are durable: `github_issue_id` (bigint) is the stable external identity; `UNIQUE (repository_id, github_issue_id) WHERE archived_at IS NULL` allows at most one current Task per stable issue per Repository while archived attempts remain unrestricted history (fresh Tasks after cancellation and after a completed issue reopens). Mutable observed address metadata (`github_issue_number`) changes through explicit UPDATE statements; identity columns are never part of such updates. GitHub presentation (issue title/state) is deliberately not stored.
- Archival and terminal outcome are separate facts: `archived_at` is NULL iff the status is nonterminal (CHECK-enforced in both directions), and `status` carries the terminal outcome. `archive_task` is the only terminal transition path — it atomically sets the terminal status, stamps `archived_at`, and rotates `state_token` — and `update_task_status` accepts nonterminal statuses only.
- Every authoritative Task-state mutation is conditional on the caller's expected `state_token` and replaces it in the same statement (`state_token = gen_random_uuid()` inside an `UPDATE ... WHERE id = %s AND state_token = %s AND archived_at IS NULL`). A mutation returns NULL when the token no longer matches or the row is missing/already archived: the operation is stale and must not be retried blindly. Translating that outcome into typed application errors is a service-layer concern, not a persistence one.
- Canonical-branch ownership is Task-level, one-time, and current-only: `UNIQUE (repository_id, canonical_feature_branch) WHERE archived_at IS NULL AND canonical_feature_branch IS NOT NULL` makes a non-null branch exclusive among a Repository's current Tasks. `create_task` always creates the branch as NULL; `bind_canonical_branch` requires a nonblank branch and applies only while `canonical_feature_branch IS NULL`, so rebinding attempts are rejected no-ops and there is no current-Task release path — archival is what releases branch ownership for future Tasks. `bind_canonical_branch` rotates the token like every other mutation. Executions (#24) may reference/observe repository state but never own the canonical branch.
- `current_plan_revision_id`/`current_owner_gate_id` are nullable UUID pointers declared without foreign keys because the PlanRevision (#23) and OwnerGate (#24) tables do not exist yet; those migrations add the foreign keys and same-Task/Workspace consistency constraints. Do not duplicate pointer-target content or outcomes on the Task row, and never add a singular current-Execution pointer.
- Query-driven indexes: `tasks_workspace_active_idx` (partial, active Workspace Tasks), `tasks_workspace_status_idx` (workspace-scoped status queries), `tasks_repository_issue_idx` (full attempt history per stable issue); the two partial unique indexes double as current-Task resolution and current canonical-branch ownership lookups. Do not add speculative indexes.
- Ordinary lifecycle archives. Owner purge of archived internal Task data is a distinct, separately authorized future operation that must never imply GitHub mutation; no purge path exists in persistence until child aggregates exist to define its cascade semantics.

## Task agent session conventions (Phase 1)

These conventions are established by the Task agent session persistence (issue #22); later issues inherit them.

- `openorc.task_agent_sessions` maps to `openorc.domain.sessions.TaskAgentSession` and carries a direct `workspace_id`; the composite foreign keys `(task_id, workspace_id) → tasks (id, workspace_id)` (the session migration adds the tasks `unique (id, workspace_id)` hook) and `(connection_id, workspace_id) → connections (id, workspace_id)` keep the direct scope in agreement with Task and Connection ownership.
- One binding per `(task_id, role)`: the UNIQUE constraint makes repeated establishment unable to create a second row. `ensure_task_agent_session` is the idempotent establishment path — insert-on-conflict-do-nothing, then reuse the existing row when it agrees on Workspace and Connection; establishing an already-bound Task/role against a different Connection raises `TaskAgentSessionDomainError` instead of silently adopting, repointing, or replacing the binding.
- Initialization coherence is CHECK-enforced in both directions: the four initialization facts (`external_session_id`, `initialized_at`, `initialization_protocol_version`, `effective_config_snapshot`) move atomically. CONNECTING requires all four NULL; READY and LOST require all four non-NULL; ENDED permits either coherent form (ended before initialization keeps all four NULL); mixed forms are rejected for every lifecycle status. `lifecycle_status = 'ended'` ⟺ `ended_at IS NOT NULL`, and `ended_at` is stamped atomically with the ENDED transition — never substituted by `updated_at`.
- No-replacement: `initialize_task_agent_session` is the only writer of `external_session_id` and applies only while `lifecycle_status = 'connecting' AND external_session_id IS NULL`. The partial unique index `(connection_id, external_session_id) WHERE external_session_id IS NOT NULL` makes one non-null external session identity non-reusable across bindings within its Connection (identities under different Connections are independent). LOST/ENDED are lifecycle states on the same row, never replacement triggers.
- Transitions are conditional updates, not triggers: lost only from READY (CONNECTING is by definition not a bound session that can be lost); ended from CONNECTING or READY; absorbing states reject further transitions by returning NULL, which must not be retried blindly (typed-error translation is a service-layer concern).
- `effective_config_snapshot` is written only from the caller-assembled explicit parameter through the domain canonicalizer and an explicit `Jsonb` adapter. Repositories never derive the snapshot from Connection rows and never write authentication material into it; raw credentials/tokens must never enter the column. No update path rewrites the snapshot after initialization: it is historical for the initialized session, and later Connection/role-binding configuration changes affect only future sessions.
- `initialize_task_agent_session` requires the complete initialization facts: a nonblank `initialization_protocol_version` and a caller-assembled `effective_config_snapshot` (an empty mapping is valid when no concrete configurable values exist). `reported_provider`/`reported_model`/`reported_runtime_version` are nullable opaque observation strings, never configuration authority, and independent of the initialization-facts coherence.
- Query-driven indexes: the `(task_id, role)` unique constraint doubles as Task-role lookup; `task_agent_sessions_connection_active_idx` (partial, `lifecycle_status IN ('connecting','ready')`) serves Connection capacity accounting; `task_agent_sessions_workspace_active_idx` (partial, same active predicate) serves active-session queries. Active occupancy is `lifecycle_status IN ('connecting','ready')`; `list_active_task_agent_sessions` provides the accounting and admission decisions belong to later services. Do not add speculative indexes.
- No privileges are granted to browser-facing roles; the schema-level lockout established by the create_openorc_schema migration carries isolation, and runtime access is backend-only.

## Planning and review conventions (Phase 1)

These conventions are established by the planning/review persistence (issue #23); later issues inherit them.

- `openorc.plan_revisions`, `openorc.review_loops`, and `openorc.review_iterations` map to `openorc.domain.planning.PlanRevision` and `openorc.domain.reviews.ReviewLoop`/`ReviewIteration`. All carry a direct `workspace_id`; composite foreign keys keep the direct scope in agreement with Task ownership and keep iteration subjects inside the loop's Task/Workspace (`(review_loop_id, task_id, workspace_id)` and `(plan_revision_id, task_id, workspace_id)` against the corresponding `unique (id, task_id, workspace_id)` hooks).
- PlanRevisions are insert-only: no repository function updates a revision; a changed plan is a fresh row with the caller-supplied next per-Task `revision_number` (the `unique (task_id, revision_number)` constraint is the durable backstop and doubles as the planning-history lookup). `repository_base_sha` is audit/context metadata — later base movement neither invalidates an accepted/authorized revision nor authorizes rewriting one.
- ReviewLoop lifecycle: created OPEN with the caller-supplied effective `iteration_limit` (no database default; the v1 default 5 lives at the configured boundary constant and is preserved on the loop for historical reconstruction). `close_review_loop` is the only transition (absorbing, conditional on `status = 'open'`, stamping the semantic `closed_at`); closure policy is orchestration's concern. `purpose` is CHECK-locked to exactly `planning` and `pr_review`; `review_loops_task_status_idx (task_id, status)` serves loop-status queries.
- ReviewIterations finalize exactly once: `record_review_iteration_result` applies only `WHERE outcome IS NULL` and atomically sets `outcome`, `summary`, `findings` (through the explicit `Jsonb` adapter with the domain-canonicalized plain list), and `decided_at = now()`. No path rewrites a finalized iteration. The finalize-coherence CHECK forbids partially recorded results, and the outcome/findings CHECK enforces ACCEPTED ⟺ zero findings and CHANGES_REQUESTED ⟺ at least one. Iteration numbering is `unique (review_loop_id, iteration_number)` (also the iteration lookup).
- `set_current_plan_revision` (in the Task repositories, with the other conditional Task mutations) moves the pointer conditionally on `expected_state_token` and rotates it; the `tasks_current_plan_revision_fk` composite foreign key `(current_plan_revision_id, id, workspace_id) → plan_revisions (id, task_id, workspace_id)` rejects cross-Task/cross-Workspace pointers with `ForeignKeyViolation` and leaves older revisions intact.
- The three tables deliberately carry no `updated_at`: immutable rows (plan revisions, finalized iterations) have no update path, and the loop's/iteration's single mutation is stamped by the semantic `closed_at`/`decided_at`. Do not add speculative indexes.
- No privileges are granted to browser-facing roles; the schema-level lockout established by the create_openorc_schema migration carries isolation.
