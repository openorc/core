# Supabase Agent Context

## Boundary

Supabase/Postgres schema, migrations, persistence integration, and Supabase Auth integration are supported core product code. Concrete production Supabase project operations belong to `openorc/cloud`.

## Migration rules

- Repository migrations are the authoritative source for schema evolution. Schema changes are authored in `supabase/migrations/` first, reviewed with the code change, and then applied to deployed Supabase projects through the supported deployment path.
- Do not mutate the live production Supabase schema first and backfill a migration afterward. Production is a deployment target, not an agent development workbench.
- Agents must not use Supabase MCP, SQL consoles, or equivalent privileged tooling to make ad hoc production DDL changes as the normal development workflow.
- Develop and validate schema changes against local Supabase or another explicitly designated non-production environment when available. The production project must be reproducible from committed migrations rather than from undocumented live edits.
- Repository migration files and applied DDL must remain aligned. If emergency/manual production repair is ever explicitly authorized, reconcile it back into the migration history immediately and document the exceptional path.
- The supported repository-native developer commands for authoring and applying migrations are documented in `docs/supabase-migrations.md`. Use those commands rather than ad hoc live-schema mutation; the Supabase CLI version is pinned exactly in `supabase/cli-version` and enforced by the tooling.
- Public-schema changes explicitly define least-privilege grants; do not rely on broad defaults.
- Never hardcode generated environment/project identifiers in product migrations.
- Project identity comes from actual environment/repository configuration, never from values inherited from any prior project.
- Schema changes require corresponding persistence/domain tests and affected generated types/contracts if such generation is adopted.

## Deletion ownership and the sanctioned Auth boundary

- The deletion-ownership migration re-declares every foreign key with an explicit, reviewed action: `ON DELETE CASCADE` for true ownership edges, `NO ACTION DEFERRABLE INITIALLY DEFERRED` for scope-consistency/cross-reference/linkage edges and the Task's upward current-object pointers. The classification is enforced by `tests/test_deletion_migration.py`; keep it reviewable rather than implicit.
- `openorc.profiles.id → auth.users (id) ON DELETE CASCADE` is the single deliberate, sanctioned exception to managed-schema isolation: the canonical account identity. Direct Supabase-administrative deletion of an auth user must remove the complete OpenOrc-owned graph (no orphaned Profile/Workspace rows from administrative deletion outside the OpenOrc application). Supabase Auth owns its own Auth/OAuth/session cleanup. The OpenOrc account-lifecycle service performs the required external cleanup/reconciliation and then converges on this same hard Auth-user deletion behavior.
- The Auth-root cascade fires only when the `auth.users` row is actually removed. Supabase soft deletion (`should_soft_delete=True`) preserves the Auth row and therefore never triggers the cascade or removes any OpenOrc data. The OpenOrc Delete Account operation must, after its required external cleanup/revocation, perform a permanent/hard Auth-user deletion — never Supabase soft deletion — or OpenOrc-owned account data is stranded.
- OpenOrc deletion must never delete or mutate GitHub engineering artifacts or runtime-owned credentials/configuration/filesystem state; the schema grants no deletion path into any external system.

## Supabase Vault

- The supported Supabase Vault extension is enabled by the `enable_supabase_vault` migration (`create extension if not exists supabase_vault cascade`). It is the concrete store for OpenOrc-owned secret purposes — the Agent Runtime control-endpoint credentials (issue #55) today and Profile-scoped GitHub App user-flow refresh credentials in the #142/#143 leaves — always through the shared exact-ID Vault storage primitive (`persistence/vault_exact_id.py`, issue #141); raw secrets never live in ordinary `openorc.*` tables.
- The enablement migration (`enable_supabase_vault`) durably locks the browser-facing roles out of Vault: PUBLIC, anon, and authenticated have no privileges on the vault schema, `vault.secrets`, `vault.decrypted_secrets`, or the secret-management functions. The migrating role needs no grants. Supabase's platform manages privileged Postgres `service_role` access to Vault (direct platform grants, re-established by platform post-create handling on hosted previews); OpenOrc deliberately accepts that trusted Supabase administrative/platform boundary rather than fighting or overriding it, and no OpenOrc application path uses Postgres `service_role` — or the Supabase secret API key (`sb_secret_...`) — to read or write runtime-control credentials. The direct backend Postgres connection is the only OpenOrc application path to Vault.
- `vault` must remain OUTSIDE the exposed Data API schemas. The platform's Data API schema exposure list is Supabase project/API configuration that repository migrations cannot enforce, so this is a deployment invariant: browser clients reach OpenOrc workflow data only through the OpenOrc application API, never through Supabase Data APIs. The schema-level revokes above deny anon/authenticated access to `vault` regardless of the exposure list.
- The effective privilege posture is proven against a real Supabase branch by integration assertions (`has_schema_privilege`/`has_table_privilege`/`has_function_privilege` in `tests/integration/test_connection_credential_services.py`): anon/authenticated denied, the backend Postgres path allowed. Postgres `service_role`'s platform-managed Vault access is accepted and deliberately not asserted; preview-deployment success alone does not prove the posture.

## Durable schema contracts

- Workspace-scoped GitHub installations and issue projections use stable external IDs for identity. Mutable repository names, issue numbers, login names, and API addresses are never the sole reconciliation key.
- GitHub hierarchy is descriptive, never Task-blocking. Explicit issue dependencies supply the blocking observation. Task source fingerprints freeze only on successful Owner Start and are never rewritten; follow the canonical migration constraint for permitted NULL states.
- Profile-scoped GitHub user authorization stores one current row per Profile, the stable same-human ID, an opaque Vault refresh reference, and a monotonic refresh generation. Active/revoked status, expiry, reference, and revocation timestamps must be coherent; no raw token column.
- Webhook delivery identity is the provider GUID, deduplicated independently of Workspace. Separate Workspace routing rows permit a single external delivery to fan out across independently configured Workspaces. Persist safe machine classification/routing facts, never webhook bodies, signatures, or secrets.
- Runtime role binding stores opaque provider/model identifiers together or neither, plus nullable verbatim role-prompt override. Runtime-reported provenance on TaskAgentSession is not an alternative configuration authority. Connection endpoints are adapter-validated non-secret `safe_config`, not a new SQL column or authorization proof.
- One-shot planning-bootstrap claims remain immutable once established; they prevent duplicate establishment dispatch but do not replace per-operation delivery identity.
- `owner_gates.status = settled` is legal only for Reviewer-settled `review_resolution` gates. Keep terminal timestamp coherence and distinct Owner decision provenance.
- The seven-type OwnerGate vocabulary (issue #258) binds per-type exact subjects durably: the three exceptional types (`block_resolution`, `github_issue_change`, `github_state_mismatch`) carry exactly one TaskBlock subject — nullable `task_block_id` with a composite FK to `task_blocks (id, task_id, workspace_id)` proving same-Task/Workspace scope, never unresolved-ness — while ordinary gates never carry a TaskBlock subject. The FK is within-Task-aggregate linkage (`NO ACTION DEFERRABLE INITIALLY DEFERRED`), never a cascade; the universal `BLOCKED`/unresolved-block/current-gate invariant and any historical backfill belong to the later integration (#250), not to the schema.
- Interrupt and canonical PR-close intents are durable, Task-scoped, exactly identified obligations, with composite subject/Workspace foreign keys and forward-only outcome states. They are not erased when the Task archives.
- The Level 2 failure-episode state (issue #251) is durably at-most-once per logical operation: `operational_failure_episodes` is unique per `(original_attempt_kind, original_attempt_id)` (an existing durable claim/attempt identity, never a Task token or mutable phase), `operational_failure_attempts` enforces `unique (episode_id, ordinal)` within the 1..3 budget and `unique (source_kind, source_attempt_id)` (at most one successor per failed attempt across the whole history), and the episode's `escalated_task_block_id` is a set-once composite-FK reference to the exact `task_blocks (id, task_id, workspace_id)` identity key (within-aggregate linkage, never a cascade). Authorized attempts are preserved history for replay prevention and later consumption, never rewritten; a consumed authorization binds its resulting Execution exactly once (`resulting_execution_id`, composite linkage FK to the executions identity key), and a later failure report about the authorization must address exactly that bound Execution.
- `tasks.terminal_cause = pr_closed_unmerged` is permitted only for an archived cancelled attempt; it is not a TaskBlock or an Owner-attributed cancellation.
- Classify every foreign key by actual ownership: true-owned children may cascade, while scope consistency, current-object pointers, and unrelated historical references must not become accidental cascades. Keep the sanctioned `auth.users` account-root deletion exception explicit.

## Security / isolation

- Workspace scope and authorization are mandatory; schema privileges cannot substitute for service authorization.
- Backend/worker secrets never reach browsers or ordinary OpenOrc tables. `vault` remains outside exposed Data API schemas; anon and authenticated roles may not access it. Supabase-managed Postgres service-role privileges are accepted platform infrastructure, not a reason to broaden grants.
- Migration behavior must be tested against representative real Postgres where constraint/privilege behavior matters. Use existing migration and integration test fixtures rather than documenting every prior issue's assertion matrix here.

Read persistence, domain/services, and API/frontend guidance when schema or authentication changes cross those boundaries. Operational commands belong in `docs/supabase-migrations.md`; constraint details belong in migrations and tests.
